## 一、基础题（3 道）

### 1. Playwright 相比 Selenium 有哪些核心优势？在实际项目中你会如何选择使用哪一种？

**参考答案**：

Playwright 相比 Selenium 的核心优势体现在以下几个方面：
- **自动等待机制**：Playwright 在执行操作（如 click、fill）前会自动检查元素是否可交互（可见、已启用、稳定、不被遮挡），而 Selenium 需要手动添加显式等待（WebDriverWait + ExpectedConditions），Playwright 大大减少了代码冗余和 flaky 问题。
- **真正的跨浏览器支持**：一套代码可以在 Chromium、Firefox、WebKit 上运行，而 Selenium 需要为不同浏览器配置不同的 driver。
- **内置高级能力**：Playwright 内置网络拦截（`page.route()`）、录制视频、Trace Viewer 调试、移动端模拟（iPhone 15 等真实设备描述符）等功能，无需额外插件。
- **无需手动管理驱动**：Playwright 自行管理和下载浏览器驱动，Selenium 需要维护 chromedriver 等驱动版本兼容性。
- **API 测试能力**：Playwright 可以直接发起 API 请求（`request` API），实现 API + UI 混合测试。

**选择策略**：如果团队需要现代化、快速执行的跨浏览器测试，且关注测试稳定性，优先选择 Playwright；如果系统需要支持 IE/旧版浏览器，或团队已有成熟的 Selenium 基础设施和插件生态，则继续使用 Selenium。

**难度**：⭐⭐ 中等

### 2. 请详细说明 pytest 中 fixture 的工作原理。它的核心价值是什么？如何实现 session 级别和 function 级别的数据管理？

**参考答案**：

pytest fixture 的核心价值在于**依赖注入**和**生命周期管理**。

- **依赖注入**：测试函数可以通过参数名自动获取 fixture 的返回值，无需手动实例化或清理。
- **生命周期管理**：使用 `yield` 可以同时定义前置（setup）和后置（teardown）逻辑。

常见作用域（scope）：
- `session` 级别：整个测试会话只执行一次（如只登录一次获取 token）
- `module` 级别：每个测试模块执行一次
- `class` 级别：每个测试类执行一次
- `function`（默认）：每个测试函数执行一次

示例：
```python
@pytest.fixture(scope="session")
def auth_token():
    """整个测试会话只登录一次，返回 token"""
    token = login_and_get_token()  # 前置操作
    yield token
    # 后置操作：清理 session 等

@pytest.fixture(scope="function")
def clean_test_data():
    """每个测试函数前后清理数据"""
    setup_test_data()  # 前置
    yield
    cleanup_test_data()  # 后置
```

在实际接口测试中，常用 session 级别的 fixture 管理登录态 Token，用 function 级别的 fixture 隔离测试数据，避免用例之间相互污染。

**难度**：⭐⭐ 中等

### 5. 在建设线上自动化回归时，如何保障测试在"真实业务链路"上运行的稳定性和安全性？线上测试的风险控制措施有哪些？

**参考答案**：

线上（生产环境）自动化回归是高风险高收益的实践，核心控制措施包括：

**1. 流量/链路隔离**：
- 优先使用"只读"链路（查询、列表、详情），避免写操作
- 如必须写，使用专门的测试账号和测试数据，限定在安全范围内
- 使用 Mock 技术拦截对下游核心系统的写请求

**2. 执行策略控制**：
- 控制并发量，避免对线上系统造成额外负载
- 选择低峰期执行（深夜定时任务）
- 设置超时和快速失败机制，避免长时间占用线上资源

**3. 数据安全**：
- 使用脱敏后的测试数据，避免触碰个人隐私数据
- 测试数据独立标记（如 UUID 前缀），便于识别和批量清理
- 不修改线上生产数据的核心业务字段

**4. 可回滚机制**：
- 测试操作前自动记录数据快照（原始状态），测试后自动还原
- 建立数据清理的定时任务，防止测试数据残留

**5. 监控与快速止损**：
- 集成监控告警，一旦自动化操作引发异常立即阻断
- 设定"熔断"条件：如连续 N 次失败自动暂停该任务
- 保留完整执行日志和录屏，便于问题回溯

**6. 灰度推进**：
- 先在 staging 环境验证脚本稳定性，再逐步灰度到线上
- 从低风险接口开始，逐步扩展到核心链路

**难度**：⭐⭐⭐ 困难

### 7. 你如何利用 Codex、Cursor、Claude Code 等 AI 工具辅助测试开发？你认为 AI 生成测试代码的局限性在哪里？如何保证 AI 生成代码的质量？

**参考答案**：

**AI 工具的典型应用场景**：
1. **测试场景生成**：输入需求描述或 API 文档，让 AI 生成补充测试场景列表覆盖边界情况
2. **测试脚本生成**：根据 API 文档（OpenAPI/Swagger）自动生成接口测试代码骨架
3. **测试数据生成**：根据字段类型和业务规则生成边界值、异常值等测试数据
4. **调试辅助**：提供失败日志/堆栈信息，让 AI 给出排查建议
5. **代码评审**：使用 Cursor/Codex 审查已编写的测试代码，发现遗漏点

**AI 生成代码的局限性**：
- **缺乏业务的深层理解**：AI 不知道业务规则背后的原因和隐式约束，可能生成"正确但无意义"的用例
- **难以处理复杂业务状态**：跨模块状态流转、业务状态机转换，AI 难以完整建模
- **质量不稳定**：不同 prompt 输入可能导致代码风格不一、可靠性不一
- **安全合规风险**：生成代码可能包含不安全写法（如硬编码凭证）

**质量保证策略**：
- **人工审查机制**：所有 AI 生成的测试代码必须经过团队技术评审（Code Review）
- **分层验证**：先生成代码 → 审查逻辑正确性 → 执行验证 → 检查能否真正发现缺陷
- **建立最佳实践模板**：团队维护标准化的测试代码模板（包括 Base 类、公共断言方法），AI 生成代码严格对齐模板
- **迭代优化 prompt**：将审查中发现的常见问题反馈到 AI 生成指南中，持续改进生成质量
- **小步提交**：AI 生成的代码分批次提交到版本控制，便于快速回滚

**难度**：⭐⭐⭐ 困难

### 8. 请实现一个接口测试框架的核心部分：编写一个 pytest fixture，实现"登录获取 token → 所有接口测试自动携带 token → 测试结束后清理"的完整逻辑，并支持 token 过期自动刷新。

**参考答案**：

```python
import time
import pytest
import requests

class TokenManager:
    """Token 管理器，支持缓存和自动刷新"""
    def __init__(self):
        self.token = None
        self.expires_at = 0

    def is_valid(self):
        return self.token and time.time() < self.expires_at - 60  # 提前60s过期

    def refresh(self):
        # 刷新 token 的逻辑
        resp = requests.post(
            "https://api.example.com/auth/refresh",
            json={"refresh_token": self.refresh_token}
        )
        data = resp.json()
        self.token = data["access_token"]
        self.expires_at = time.time() + data["expires_in"]
        return self.token

@pytest.fixture(scope="session")
def token_manager():
    """session 级别的 token 管理器"""
    tm = TokenManager()
    tm.refresh()
    yield tm
    # 后置清理
    tm.token = None

@pytest.fixture()
def api_client(token_manager):
    """每个测试函数获取一个带 token 的 API 客户端"""
    class APIClient:
        def __init__(self):
            self.session = requests.Session()
        
        def request(self, method, url, **kwargs):
            # 检查 token 是否过期，过期自动刷新
            if not token_manager.is_valid():
                token_manager.refresh()
            self.session.headers["Authorization"] = f"Bearer {token_manager.token}"
            return self.session.request(method, url, **kwargs)
    
    return APIClient()
```

**核心设计要点**：
- 使用 `yield` 实现前置（登录）和后置（清理）
- session scope 保证整个测试会话只登录一次，避免频繁登录导致性能瓶颈
- token 过期自动刷新，保证长时间运行的测试任务不会因 token 过期而大面积失败
- 封装 `api_client`，对测试函数屏蔽底层细节

**难度**：⭐⭐⭐ 困难

### 10. 请实现一个 Python 函数，用于对一组 HTTP API 的响应进行自动化断言校验。要求支持：① 响应状态码校验；② JSON 字段存在性校验；③ 字段类型校验；④ 字段值大小比较；⑤ 可扩展的自定义校验规则。

**参考答案**：

```python
import json
from typing import Any, Callable, Dict, List

class APIAssertionError(AssertionError):
    """自定义断言异常，用于更清晰的错误信息"""
    pass

class ResponseValidator:
    """API 响应验证器"""
    
    def __init__(self, response_data: Any):
        self.data = response_data
    
    @classmethod
    def from_response(cls, response: Any):
        """从 requests.Response 创建验证器"""
        try:
            data = response.json()
        except json.JSONDecodeError:
            data = response.text
        return cls(data)
    
    def assert_status(self, expected_status: int, actual_status: int):
        """校验状态码"""
        if actual_status != expected_status:
            raise APIAssertionError(
                f"状态码不匹配: 期望 {expected_status}, 实际 {actual_status}"
            )
        return self
    
    def assert_field_exists(self, field: str, data: dict = None):
        """校验字段存在性（支持点号路径，如 'data.user.name'）"""
        current = data if data is not None else self.data
        keys = field.split(".")
        for key in keys:
            if not isinstance(current, dict) or key not in current:
                raise APIAssertionError(f"字段 '{field}' 不存在")
            current = current[key]
        return self
    
    def assert_field_type(self, field: str, expected_type: type):
        """校验字段类型"""
        keys = field.split(".")
        current = self.data
        for key in keys:
            current = current[key]
        if not isinstance(current, expected_type):
            raise APIAssertionError(
                f"字段 '{field}' 类型不匹配: 期望 {expected_type.__name__}, "
                f"实际 {type(current).__name__}"
            )
        return self
    
    def assert_field_compare(self, field: str, operator: str, expected_value: Any):
        """字段值比较"""
        keys = field.split(".")
        current = self.data
        for key in keys:
            current = current[key]
            
        operations = {
            ">": lambda a, b: a > b,
            ">=": lambda a, b: a >= b,
            "<": lambda a, b: a < b,
            "==": lambda a, b: a == b,
            "!=": lambda a, b: a != b,
            "in": lambda a, b: a in b,
            "contains": lambda a, b: b in a,
        }
        if operator not in operations:
            raise ValueError(f"不支持的比较运算符: {operator}")
        if not operations[operator](current, expected_value):
            raise APIAssertionError(
                f"字段 '{field}' 断言失败: 实际值 {current} "
                f"不满足条件 {operator} {expected_value}"
            )
        return self
    
    def assert_custom(self, field: str, validator: Callable[[Any], bool], description: str = ""):
        """自定义校验规则"""
        keys = field.split(".")
        current = self.data
        for key in keys:
            current = current[key]
        if not validator(current):
            raise APIAssertionError(
                f"字段 '{field}' 自定义断言失败: {description}"
            )
        return self


# 使用示例
def test_create_order():
    resp = api_client.post("/api/orders", json={...})
    
    validator = ResponseValidator.from_response(resp)
    validator.assert_status(200, resp.status_code)
    validator.assert_field_exists("data.order_id")
    validator.assert_field_type("data.order_id", str)
    validator.assert_field_compare("data.amount", ">", 0)
    validator.assert_field_compare("data.amount", "<", 100000)
    validator.assert_custom(
        "data.status", 
        lambda s: s in ["PENDING", "PAID"],
        "状态值必须为 PENDING 或 PAID"
    )
```

**核心设计亮点**：
- **链式调用**：所有 `assert_*` 方法返回 `self`，支持链式断言
- **点号路径**：支持嵌套 JSON 字段的深度访问（如 `data.user.name`）
- **可扩展性**：`assert_custom` 允许传入任意校验函数，支持业务自定义规则
- **清晰错误信息**：断言失败抛出包含具体字段名和期望/实际值的异常，便于 CI 日志排查
