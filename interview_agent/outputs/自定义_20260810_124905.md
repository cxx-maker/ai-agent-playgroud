### 1. 请详细说明 pytest 中 `fixture`、`parametrize` 和 `conftest.py` 的用法与区别，以及它们如何支撑测试平台的用例管理和数据驱动。

**参考答案**：

- **fixture**：pytest 的依赖注入机制，用于提供测试前置条件（如数据库连接、登录态、临时数据）。支持 `scope` 参数（`function`/`class`/`module`/`session`）控制生命周期，支持 `yield` 实现 setup/teardown。例如：
  ```python
  @pytest.fixture(scope="session")
  def db_conn():
      conn = create_connection()
      yield conn
      conn.close()
  ```
- **parametrize**：数据驱动测试的核心装饰器，可对同一测试逻辑传入多组数据，有效提升用例复用性。例如：
  ```python
  @pytest.mark.parametrize("username,password,expected", [
      ("admin", "123456", 200),
      ("user", "wrong", 401)
  ])
  def test_login(username, password, expected): ...
  ```
- **conftest.py**：pytest 的钩子文件，可被同目录及子目录的测试文件自动发现，存放全局 fixture、自定义插件、命令行参数扩展等。适合在测试平台中统一管理环境配置、登录 token、mock 数据等公共能力。

**在测试平台中的应用**：fixture 用于管理测试资源和环境隔离，parametrize 支撑测试数据的批量注入和组合覆盖，conftest.py 定义平台的全局配置和钩子，三者结合可实现用例的标准化、可配置和可复用。

**难度**：⭐⭐ 中等

### 2. 在测试平台中，如何处理自动化用例的"失败重跑"（flaky test 治理）？请从技术方案、设计考量和工程最佳实践三个层面回答。

**参考答案**：

**技术方案层面**：
- **用例级重跑**：使用 pytest-rerunfailures 插件，对失败用例设置最大重试次数和间隔，如 `@pytest.mark.flaky(reruns=3, reruns_delay=2)`。
- **平台层重跑**：在测试平台的任务调度模块中设计重跑策略，首次失败自动触发重跑，并将重跑结果和首次失败日志分别存储，便于分析。
- **分组重跑**：将失败用例按错误类型（如超时、断言失败、环境问题）分组，对不同类别采用差异化重跑策略。

**设计考量**：
- 需要区分**真缺陷**和**flaky**——设计"稳定性判定"机制，如同一用例连续N次重跑仍失败则判定为缺陷触发告警，而非无限重试掩盖问题。
- 重跑数据要回写平台，记录失败率、重跑率、平均耗时，用于后续的稳定性优化。

**工程最佳实践**：
- 通过 Playwright 的自动等待（auto-waiting）和 `expect` 轮询机制从源头减少 UI 层面的 flaky。
- 使用 `page.route()` 对不稳定的第三方接口做 mock，确保测试的确定性。
- 对历史 flaky 用例建立"红名单"机制，定期清理或重构。
- 将重跑策略配置化，不同任务（如冒烟、回归、发布验证）使用不同的重跑参数。

**难度**：⭐⭐ 中等

### 3. 请对比 Playwright 与 Selenium 的架构差异和适用场景，并说明在测试平台建设中为什么越来越多团队选择 Playwright。

**参考答案**：

| 维度 | Playwright | Selenium |
|------|-----------|----------|
| **架构** | 基于 CDP（Chrome DevTools Protocol）直接与浏览器通信，使用 WebSocket 连接 | 通过 WebDriver 协议，需要各浏览器驱动（chromedriver/geckodriver）作为中介 |
| **等待机制** | 内置自动等待（auto-waiting），执行操作前自动检查元素可见、可交互、稳定 | 需要手动显式等待（WebDriverWait + ExpectedConditions） |
| **调试能力** | 内置录屏、trace viewer、代码生成（codegen） | 需要额外插件，调试能力较弱 |
| **多浏览器** | 一套代码跨 Chrome/Firefox/Safari/WebKit | 需要分别配置各浏览器驱动 |
| **网络控制** | 原生支持 `page.route()` 拦截/修改网络请求，Mock API 能力强大 | 需要通过 BrowserMob 等第三方代理实现 |
| **多语言支持** | Python/JS/Java/.NET | Python/JS/Java/C#/Ruby 等更广 |

**适用场景**：
- **Playwright** 适合：复杂的现代 Web 应用（SPA、PWA）、需要网络 mock 的场景、跨浏览器覆盖需求高、需要与 CI/CD 深度集成的团队。
- **Selenium** 适合：已有大量存量 Selenium 脚本的团队、需要支持老版本浏览器的场景、团队维护成本考量。

**测试平台选型考量**：Playwright 的 Trace Viewer 和自动等待机制极大减少了脚本维护成本，其 `expect()` 内置轮询重试和失败快照能力使其天然适配"失败重跑"场景，同时原生支持 API testing 和移动端模拟，一套框架同时覆盖 Web UI + API 测试，平台集成成本更低。

**难度**：⭐⭐ 中等

### 5. 线上环境的自动化回归测试和测试环境有什么本质区别？你是如何设计线上自动化方案来保障核心业务链路稳定的？

**参考答案**：

**本质区别**：

| 维度 | 测试环境 | 线上环境 |
|------|----------|----------|
| **数据风险** | 可随意造数、删除 | 只能只读查询或通过已授权接口创建数据，严禁对用户数据操作 |
| **影响面** | 操作失败影响有限 | 误操作可能影响真实用户和业务 |
| **环境依赖** | 可灵活部署、Mock | 依赖真实模块和第三方 |
| **执行限制** | 可随时执行 | 需要在低峰期，避免高峰期干扰 |
| **监控必要性** | 较低 | 高，需配套告警 |

**线上自动化方案设计**：

1. **分层策略**：
   - **API 健康巡检**（最小成本、最高频）：对核心接口做只读型 GET 请求验证状态码、响应时间、数据结构完整性。
   - **业务链路验证**：设计销售链路场景（如浏览→加购→下单）但**不回写真实数据**，采用影子数据或事务回滚机制。
   - **Synthetic Monitoring（合成监控）**：将关键页面流程转化为定时 Playwright 用例，7×24小时执行，配合告警规则第一时间发现线上问题。

2. **数据安全设计**：
   - 使用专用测试账号 + 只读数据库权限。
   - 所有写操作使用 `test_` 前缀的数据标识，任务结束后自动清理。
   - 对线上数据库只允许 SELECT 查询用于验证，严禁 INSERT/UPDATE/DELETE。

3. **降级与熔断**：
   - 线上自动化发现异常时，先触发告警 → 人工确认 ---> 视严重程度触发发布回滚，形成闭环。

4. **指标观测**：记录线上用例的 P95 响应时间、失败率、MTTI（平均发现时间），作为质量度量核心数据。

- 提供明确上下文（框架版本、现有代码风格、PO模式规范），让 AI 生成基于现有框架的测试代码。

- 将失败日志 + trace 信息粘贴给 AI，请求分析根因和修复建议。
- **质量保障**：AI 给出修复建议后，强制要求它提供"为什么这样改"的逻辑链，人工验证修复方案是否覆盖了真实问题而不是只掩盖了表面现象。对 AI 修复的脚本，必须以实际运行通过 + 维护回归记录为验收标准。

**经验数据**：在我的实践中，AI 辅助可将测试脚本编写效率提升约 60%，但 AI 生成代码的首次通过率约为 70-80%，剩余 20-30% 需要人工调试修正。因此，**AI 不能替代测试设计决策和最终质量判断，它是效率放大器而非质量保证者**。

### 7. 请描述你在 CI/CD 流水线中集成自动化测试的完整设计。包括流水线阶段划分、质量门禁（Quality Gate）的设定、失败告警与缺陷闭环机制。

**参考答案**：

**流水线阶段设计**：

```
代码提交 → 静态检查（Lint/SonarQube） → 单元测试 → 构建打包 
→ 部署至测试环境 → API冒烟测试 → UI核心链路测试 → 全量回归测试 
→ 发布至预发布环境 → 发布验证自动化 → 灰度发布 → 线上健康巡检
```

**质量门禁（Quality Gate）设定**：
- 单元测试覆盖率 ≥ 80%（核心模块达标率）。
- API 测试通过率 100% 为阻塞级，不允许放行。
- UI 测试允许轻微 flaky，但同一用例连续 3 次失败则阻塞发布。
- 代码规范检查（SonarQube）阻断级问题数 = 0。
- 新增功能必须有对应自动化用例，否则 CI 拒绝合入（测试左移）。

**工具链选型**：GitLab CI 或 GitHub Actions 作为流水线引擎，Jenkins 管理复杂任务（测试平台对接），Allure 生成测试报告，SonarQube 做代码质量检查。

**失败告警与缺陷闭环**：
- **多级告警**：测试失败 → 自动发送 IM 通知（钉钉/企微），标记失败等级：冒烟失败为 P0 紧急、回归失败为 P1 重要、非关键用例失败为 P2 一般。
- **自动提单**：通过 API 将失败用例自动创建为 JIRA/禅道工单，附带失败截图、堆栈日志、重跑记录和 Trace 链接。
- **闭环机制**：每个缺陷必须关联"修复验证"和"回归确认"两步。修复后由 CI 自动重新执行对应用例，通过后自动关闭工单。同时建立"缺陷-用例"映射，防止同类缺陷漏测。
- **数据驱动改进**：定期统计 CI 中自动化测试的**拦截率**（缺陷在 CI 中被发现的占比）、**漏网率**（线上缺陷/总缺陷），持续优化测试策略。

## 三、算法题（3题）

### 8. 假设你有 N 个测试用例，执行时间分别为 `t[i]`，依赖关系构成了一个有向无环图（DAG）。现有多台并行执行器，请设计一个算法，在最大化并行度的同时，使得总执行时间最小（关键路径调度问题）。

**参考答案**：

**问题本质**：这是一个**带优先级的任务调度问题**（DAG 调度 + 多机并行），目标是最小化 Makespan（总完成时间）。

**算法设计思路**：

**方法一：关键路径优先调度（CPFS - Critical Path First Scheduling）**

```
1. 对 DAG 做拓扑排序，并计算每个用例的最早开始时间（EST）和最晚完成时间（LST）。
2. 计算关键路径：在 DAG 中找到总执行时间最长的路径（从起点到终点）。
3. 优先将关键路径上的用例分配给执行器（不延迟任务）。
4. 非关键路径上的用例，利用空闲时间片择机调度。
```

**方法二：分层调度 + 贪心分配**

```
1. 拓扑排序将用例按"层"分组（同层之间无依赖）。
2. 对每一层内的用例按执行时间降序排列（长任务优先，类似 Longest Processing Time 算法）。
3. 将用例分配给当前空闲的执行器（贪心赋值）。
4. 下一层等上一层全部完成后开始（或用例级别依赖控制）。
```

**伪代码示例**（基于拓扑排序 + 关键路径）：

```python
import heapq
from collections import deque

def schedule_tasks(tasks, deps, num_workers):
    """
    tasks: {id: duration}
    deps:  [(pre, post)] 依赖关系表
    num_workers: 执行器数量
    返回: 安排计划和总耗时
    """
    # 1. 构建邻接表和入度
    graph = {t: [] for t in tasks}
    indegree = {t: 0 for t in tasks}
    for pre, post in deps:
        graph[pre].append(post)
        indegree[post] += 1
    
    # 2. 拓扑排序获取执行顺序
    queue = deque([t for t in tasks if indegree[t] == 0])
    order = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for succ in graph[node]:
            indegree[succ] -= 1
            if indegree[succ] == 0:
                queue.append(succ)
    
    # 3. 贪心调度到多执行器（最小堆维护执行器空闲时间）
    workers = [(0, i) for i in range(num_workers)]  # (空闲时间, worker_id)
    heapq.heapify(workers)
    schedule = {}
    latest_finish = 0
    
    # 按拓扑顺序逐一分配
    for task in order:
        # 找到最早空闲且满足依赖的执行器
        start_time, worker = heapq.heappop(workers)
        # 处理依赖约束（父任务必须优先完成）
        if task in task_deps:
            start_time = max(start_time, task_deps[task])
        
        end_time = start_time + tasks[task]
        schedule[task] = (worker, start_time, end_time)
        heapq.heappush(workers, (end_time, worker))
        latest_finish = max(latest_finish, end_time)
    
    return schedule, latest_finish
```

**复杂度分析**：拓扑排序 O(V+E)，贪心分配 O(V log K)（K 为执行器数）。整体时间复杂度为 O(V log K + E)，空间 O(V+E)。

**测试平台实际应用**：在测试平台的执行器调度中，将用例按依赖关系建模为 DAG，通过上述算法算出最优调度方案。如果用例数量多（千级），可以进一步做**分簇优化**——将同一模块的用例聚类，减少调度切换开销。对于测十分庞大的场景（如全量回归1000+用例），可以使用模拟退火或遗传算法进一步优化（通过牺牲部分最优性换取运行效率）。

**难度**：⭐⭐⭐ 困难

### 9. 给定一个测试报告数据列表，每个元素包含 `{suite_name, status, duration}`，请编写一个 Python 函数：统计各测试套件的通过率、平均耗时，并按通过率升序、耗时降序排序输出。同时要求对通过率为 0 的套件标记为"需要关注"。

**参考答案**：

```python
from typing import List, Dict, Any
from collections import defaultdict

def analyze_test_report(test_data: List[Dict[str, Any]]) -> List[Dict[str, Any]]:
    """
    分析测试报告数据
    
    Args:
        test_data: [{"suite_name": "auth", "status": "PASS"/"FAIL", "duration": 1.5}, ...]
    
    Returns:
        [{"suite_name": "...", "pass_rate": 0.8, "avg_duration": 2.1, "needs_attention": False}, ...]
    """
    # 1. 按套件聚合统计
    stats = defaultdict(lambda: {"total": 0, "passed": 0, "total_duration": 0.0})
    
    for item in test_data:
        suite = item["suite_name"]
        stats[suite]["total"] += 1
        if item["status"].upper() == "PASS":
            stats[suite]["passed"] += 1
        stats[suite]["total_duration"] += item["duration"]
    
    # 2. 计算指标并构造结果
    results = []
    for suite, s in stats.items():
        pass_rate = s["passed"] / s["total"] if s["total"] > 0 else 0.0
        avg_duration = s["total_duration"] / s["total"] if s["total"] > 0 else 0.0
        results.append({
            "suite_name": suite,
            "pass_rate": round(pass_rate, 2),
            "avg_duration": round(avg_duration, 2),
            "needs_attention": pass_rate == 0.0  # 通过率为0标记
        })
    
    # 3. 排序: 通过率升序 → 耗时降序 (多键排序)
    results.sort(key=lambda x: (x["pass_rate"], -x["avg_duration"]))
    
    return results

# 使用示例

    {"suite_name": "auth", "status": "FAIL", "duration": 2.5},
    {"suite_name": "payment", "status": "FAIL", "duration": 3.0},
```

### 10. 请用 Python 实现一个接口测试的重试机制：对指定 API，在请求失败或返回状态码非 200 时，最多重试三次，每次间隔呈指数递增（如 1s → 2s → 4s），同时在重试过程中将错误信息记录到列表，最终返回最后一次的响应和重试日志。

**参考答案**：

```python
import time
import requests
from typing import Any, Dict, List, Optional, Tuple
import logging

logger = logging.getLogger(__name__)

def api_call_with_retry(
    url: str,
    method: str = "GET",
    max_retries: int = 3,
    base_interval: float = 1.0,
    timeout: int = 10,
    **kwargs: Any
) -> Tuple[Optional[requests.Response], List[Dict[str, Any]]]:
    """
    带指数退避重试的 API 调用
    
    Args:
        url: 请求地址
        method: HTTP方法
        max_retries: 最大重试次数（不含首次请求）
        base_interval: 基础等待间隔（秒）
        timeout: 超时时间
        **kwargs: 请求参数（headers, json, params等）
    
    Returns:
        (最终响应对象或None, 重试日志列表)
    """
    retry_logs: List[Dict[str, Any]] = []
    response: Optional[requests.Response] = None
    
    for attempt in range(max_retries + 1):  # 首次 + 重试 max_retries 次
        try:
            logger.info(f"Attempt {attempt + 1}/{max_retries + 1} - {method} {url}")
            response = requests.request(
                method=method,
                url=url,
                timeout=timeout,
                **kwargs
            )
            
            if response.status_code == 200:
                retry_logs.append({
                    "attempt": attempt + 1,
                    "status_code": response.status_code,
                    "error": None,
                    "elapsed": response.elapsed.total_seconds()
                })
                return response, retry_logs
            elif attempt < max_retries:
                # 非200状态码，记录错误
                error_msg = f"HTTP {response.status_code}: {response.text[:100]}"
                retry_logs.append({
                    "attempt": attempt + 1,
                    "status_code": response.status_code,
                    "error": error_msg,
                    "elapsed": response.elapsed.total_seconds()
                })
                # 指数退避
                wait_time = base_interval * (2 ** attempt)
                logger.warning(f"Request failed ({error_msg}), retrying in {wait_time}s...")
                time.sleep(wait_time)
            else:
                retry_logs.append({
                    "attempt": attempt + 1,
                    "status_code": response.status_code,
                    "error": f"HTTP {response.status_code}: {response.text[:100]}",
                    "elapsed": response.elapsed.total_seconds()
                })
                break
                
        except (requests.ConnectionError, requests.Timeout) as e:
            error_msg = f"{type(e).__name__}: {str(e)}"
            retry_logs.append({
                "attempt": attempt + 1,
                "status_code": None,
                "error": error_msg,
                "elapsed": 0.0
            })
            
            if attempt < max_retries:
                wait_time = base_interval * (2 ** attempt)
                logger.warning(f"Request error ({error_msg}), retrying in {wait_time}s...")
                time.sleep(wait_time)
            else:
                logger.error(f"All retries exhausted. Last error: {error_msg}")
    
    return response, retry_logs


# 使用示例
if __name__ == "__main__":
    resp, logs = api_call_with_retry(
        url="https://api.example.com/v1/health",
        max_retries=3,
        base_interval=1.0
    )
    
    if resp and resp.status_code == 200:
        print("API调用成功:", resp.json())
    else:
        print("所有重试均失败")
        for log in logs:
            print(f"  第{log['attempt']}次: status={log['status_code']}, error={log['error']}")
```

**关键设计点**：
- **指数退避**：`base_interval * (2 ** attempt)`，即 1s → 2s → 4s，避免对服务造成二次压力。
- **区分错误类型**：网络异常（ConnectionError/Timeout）和 HTTP 非 200 分开记录，便于后续分析。
- **日志完整**：每一次尝试的状态码、错误信息、耗时都被记录，用于失败原因分析。
- **边界处理**：max_retries=0 时仅执行一次；网络异常时 response 为 None 也不触发 TypeError。
- **可扩展性**：可进一步支持 `retry_on = [500, 502, 503]` 指定哪些状态码触发重试（如部分 4xx 不重试，因为重试无意义），这是测试平台中处理第三方 API 不稳定性的常见需求。

**难度**：⭐⭐ 中等
