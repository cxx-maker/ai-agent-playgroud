### 1. Playwright 相比 Selenium 的核心优势是什么？在什么场景下你仍会考虑使用 Selenium？

**参考答案**：

**Playwright 的核心优势**：
1. **自动等待机制**：执行操作（click、fill）前自动检查元素是否可交互（可见、已启用、稳定、不被遮挡），大幅减少显式等待的使用频率
2. **真正的跨浏览器**：同一套代码可在 Chromium、Firefox 和 WebKit 上运行，无需额外配置驱动（内置浏览器管理）
3. **执行效率更高**：尤其擅长并行执行、网络控制和智能等待场景
4. **内置丰富的测试能力**：网络拦截与 Mock（route）、视频录制、Trace Viewer 调试、移动端模拟（devices 内置 iPhone 15 等真实设备描述符）
5. **统一 API 测试能力**：支持直接在 Playwright 中发起 API 请求，实现 UI + API 混合测试

**仍然使用 Selenium 的场景**：
- 需要兼容 IE 或旧版 Edge 的遗留系统
- 已有大量基于 Selenium 的历史测试资产，迁移成本过高
- 某些特殊的企业级集成场景（如银行核心系统）
- 团队技术栈强绑定 Java + Selenium 生态

**难度**：⭐⭐ 中等

### 2. 请分别说明 pytest 中 `fixture`、`parametrize`、`conftest.py` 的用途，并用代码示例说明如何处理测试数据依赖和接口 Token 传递。

**参考答案**：

**Fixture**：用于管理测试的前置条件（setup）和清理（teardown），支持作用域控制（`function`/`class`/`module`/`session`）和依赖注入。

**Parametrize**：实现数据驱动测试，通过 `@pytest.mark.parametrize` 将多组数据注入同一测试函数。

**conftest.py**：pytest 的局部配置文件，在该目录及子目录下自动加载，用于定义全局 fixtures、hook 函数和插件配置。

**接口 Token 传递实例**：

```python
# conftest.py
import pytest
import requests

@pytest.fixture(scope="session")
def base_url():
    return "https://api.example.com"

@pytest.fixture(scope="session")
def auth_token(base_url):
    """登录获取 token，仅执行一次"""
    resp = requests.post(f"{base_url}/login", json={"user": "admin", "pass": "123456"})
    assert resp.status_code == 200
    return resp.json()["token"]

@pytest.fixture
def session(auth_token):
    """带认证的会话，每个测试函数独立"""
    s = requests.Session()
    s.headers.update({"Authorization": f"Bearer {auth_token}"})
    yield s
    s.close()

# test_order.py
import pytest

@pytest.mark.parametrize("order_id", ["1001", "1002", "1003"])
def test_query_order(session, base_url, order_id):
    resp = session.get(f"{base_url}/orders/{order_id}")
    assert resp.status_code == 200
    assert resp.json()["id"] == order_id
```

**关键要点**：
- `scope="session"` 确保 token 只获取一次，提高执行效率
- `session` fixture 每次测试独立创建，避免环境污染
- 参数化与 fixture 结合可以实现数据驱动 + 状态管理的完整模式

**难度**：⭐⭐ 中等

### 3. 在设计测试用例时，"等价类划分"和"边界值分析"的作用是什么？请以"用户注册时密码长度为 8-20 位，且必须包含字母和数字"为例说明完整的设计思路。

**参考答案**：

**等价类划分**：将输入域划分为若干有效/无效等价类，从每个类中选取代表性数据进行测试，避免无穷尽的用例输入。

**边界值分析**：关注输入边界的临界区域（上点、内点、离点），因为大量缺陷发生在边界附近。

**针对示例需求的分析**：

| 维度 | 有效等价类 | 无效等价类 |
|------|-----------|-----------|
| 长度 | 8-20位 | <8位、>20位 |
| 字符组成 | 含字母和数字 | 仅字母、仅数字、含特殊字符 |
| 边界值 | 8位、20位 | 7位、21位、0位（空） |

**设计用例**：
1. 8位且含字母数字 → 通过（上边界内点）
2. 20位且含字母数字 → 通过（上边界内点）
3. 7位（含字母数字）→ 失败（长度下边界离点）
4. 21位（含字母数字）→ 失败（长度上边界离点）
5. 8位纯数字 → 失败（缺少字母）
6. 8位纯字母 → 失败（缺少数字）
7. 空密码 → 失败（空值处理）
8. 20位含字母数字和特殊字符 → 通过（验证字符规则兼容性）

**工程经验**：除功能用例设计外，还需考虑异常场景（如密码明文传输日志泄露）、数据一致性（数据库存储长度与校验规则一致）等。

**难度**：⭐ 简单

### 5. 在线上自动化回归建设中，如何保证测试的稳定性和可靠性？请结合你在实际项目中遇到的 flaky test 问题，详述你的排查和解决方案。

**参考答案**：

**线上回归的稳定性挑战**：
- 网络波动、第三方依赖不稳定
- 异步加载导致元素时序问题
- 测试数据冲突（并发执行时的数据竞争）
- 环境差异（DNS、CDN、灰度策略）
- 浏览器/设备兼容性问题

**排查 flaky test 的系统性方法**：

1. **数据驱动分析**：收集失败率、失败模式（固定步骤失败vs随机失败）、失败环境分布
2. **日志与截图证据链**：Playwright Trace Viewer 回放执行过程，定位是元素未找到、超时、还是断言不一致
3. **隔离验证法**：单独运行失败用例，判断是并发干扰还是用例本身问题
4. **代码审查**：检查是否使用了不稳定的定位符（如固定顺序的 CSS 选择器），或缺少幂等性处理

**典型解决方案**：

```python
# Playwright 中的稳定性增强示例
import pytest
from playwright.sync_api import sync_playwright

def test_async_load_scene(page):
    # 1. 使用等待网络空闲，确保异步数据加载完成
    page.goto("https://example.com", wait_until="networkidle")
    
    # 2. 使用面向用户的定位器，而非脆弱的 XPath
    page.get_by_role("button", name="提交订单").click()
    
    # 3. 使用 expect 的自动重试机制进行断言
    expect(page.get_by_text("订单创建成功")).to_be_visible(timeout=10000)
    
    # 4. 对于第三方依赖，使用 route 进行 Mock 拦截
    page.route("**/api/third-party/**", lambda route: route.fulfill(
        json={"status": "mock_success"}
    ))
```

**重试策略的最佳实践**：
- 区分"环境性失败"和"功能性失败"：环境性失败自动重试，功能性失败立即停止
- 设置重试上限（如最多 3 次）、间隔时间（指数退避）和重试条件白名单
- 对 flaky 率超过阈值的用例自动标记，纳入维护队列

**难度**：⭐⭐⭐ 困难

### 6. 请描述你如何将自动化测试接入 CI/CD 流水线，包括触发策略、质量门禁（Quality Gate）设计和失败告警机制。

**参考答案**：

**接入 CI/CD 的完整设计**：

**1. 触发策略**：
- **代码提交触发（CI）**：每次 PR 合入主分支后，触发快速冒烟测试（10分钟内完成）
- **定时回归**：每晚执行全量回归（覆盖 API、Web UI、核心业务链路）
- **发布验证**：版本上线前执行发布前置检查（P0 优先级用例）
- **手动触发**：支持指定分支、指定用例集执行

**2. CI/CD Pipeline 设计（示例）**：

```yaml
# GitLab CI 示例
stages:
  - build
  - api_test
  - ui_test
  - quality_gate
  - deploy

api_test:
  stage: api_test

    - pytest tests/api -m "not slow" --junitxml=report.xml
  artifacts:

    - merge_requests

ui_test:
```

**3. 质量门禁设计**：
- **硬性门槛**：P0 用例 100% 通过、总通过率 >= 95%

- **分层门禁**：单元测试 > API 测试 > UI 测试，每层失败即阻断后续流程

**4. 失败告警机制**：
- **通知渠道**：钉钉/飞书/企业微信机器人推送失败摘要
- **告警分级**：
  - P0 故障：立即推送 + 电话提醒
  - 常规失败：汇总到每日报告
  - Flaky：单独归类，不打扰
- **缺陷闭环**：失败测试自动关联 GitLab Issue，修复后自动关闭

**5. 度量与回顾**：
- 每日/每周自动化回归报告：通过率、耗时、关键指标趋势
- 新缺陷发现率分析，评估自动化投入产出比

### 8. 请用 Python 实现一个支持"指数退避"（Exponential Backoff）的重试机制，要求支持最大重试次数和超时时间，并能区分"可重试错误"和"不可重试错误"。

**参考答案**：

```python
import time
import random
from functools import wraps


class RetryableError(Exception):
    """可重试异常类型"""
    pass


class NonRetryableError(Exception):
    """不可重试异常类型"""
    pass


def retry_with_backoff(
    max_retries: int = 3,
    base_delay: float = 1.0,
    max_delay: float = 30.0,
    backoff_factor: float = 2.0,
    jitter: bool = True,
    retryable_exceptions: tuple = (RetryableError, ConnectionError, TimeoutError),
):
    """
    带指数退避的重试装饰器
    
    Args:
        max_retries: 最大重试次数
        base_delay: 基础延迟时间（秒）
        max_delay: 最大延迟时间（秒）
        backoff_factor: 退避因子
        jitter: 是否添加随机抖动，避免惊群效应
        retryable_exceptions: 可重试的异常类型
    """
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(max_retries + 1):
                try:
                    return func(*args, **kwargs)
                except retryable_exceptions as e:
                    if attempt >= max_retries:
                        raise e
                    delay = min(base_delay * (backoff_factor ** attempt), max_delay)
                    if jitter:
                        delay *= random.uniform(0.5, 1.5)
                    print(f"[Retry] attempt={attempt+1}/{max_retries}, "
                          f"error={e}, waiting {delay:.2f}s")
                    time.sleep(delay)
                except NonRetryableError as e:
                    raise e
        return wrapper
    return decorator


# 使用示例
@retry_with_backoff(max_retries=3, base_delay=0.5)
def query_order_api(order_id: str) -> dict:
    resp = requests.get(f"https://api.example.com/orders/{order_id}", timeout=5)
    if resp.status_code == 500:
        raise RetryableError(f"Server 500 error for order {order_id}")
    if resp.status_code == 400:
        raise NonRetryableError(f"Bad request for order {order_id}, no point retrying")
    return resp.json()


# 使用 pytest-rerunfailures 时更简洁
import pytest

@pytest.mark.flaky(reruns=3, reruns_delay=1, 
                   only_rerun=["ConnectionError", "TimeoutError"])
def test_query_order():
    # 仅对网络类错误重试
    ...
```

**关键考点**：
- 退避算法的时间复杂度：第 n 次等待时间为 `base_delay * factor^(n-1)`
- 是否需要 jitter（随机抖动）：避免多个并发任务同一时刻重试造成"惊群效应"
- 重试 vs 幂等性：重试的前提是操作是幂等的（如 GET 请求可以安全重试，POST 创建订单则需考虑重复创建风险）

**难度**：⭐⭐ 中等

### 9. 请编写一个 Python 函数，用于从大量日志文件中统计指定错误模式（如 `ERROR` 或正则 `Exception: (.*?)`）出现的频次和分布，要求内存占用可控。请考虑使用生成器、正则匹配和 `collections.Counter` 等技巧。

**参考答案**：

```python
import re
import glob
from collections import Counter
from pathlib import Path


def analyze_log_errors(log_dir: str, pattern: str = r"\[ERROR\].*?Exception:\s*(\w+)") -> dict:
    """
    从日志文件目录中统计错误类型频次分布
    
    Args:
        log_dir: 日志文件目录路径（支持 glob 通配符）
        pattern: 错误提取正则，默认提取 'Exception: XxxError' 中的异常类型
    
    Returns:
        {
            "total_files": int,
            "total_errors": int,
            "error_distribution": Counter,  # 错误类型 -> 次数
            "top_errors": list,             # Top 10 错误
            "files_by_error_count": Counter # 文件 -> 错误数
        }
    """
    compiled = re.compile(pattern)
    error_counter = Counter()
    file_counter = Counter()
    total_errors = 0
    
    # 使用 yield from 逐行读取，避免一次性将整个大文件加载到内存
    def read_lines(file_path: str):
        """生成器：逐行读取文件"""
        with open(file_path, "r", encoding="utf-8", errors="ignore") as f:
            for line in f:
                yield line
    
    for file_path in glob.glob(f"{log_dir}/**/*.log", recursive=True):
        file_errors = 0
        for line in read_lines(file_path):
            match = compiled.search(line)
            if match:
                error_type = match.group(1)
                error_counter[error_type] += 1
                file_errors += 1
                total_errors += 1
        file_counter[file_path] = file_errors
    
    return {
        "total_files": len(file_counter),
        "total_errors": total_errors,
        "error_distribution": error_counter,
        "top_errors": error_counter.most_common(10),
        "files_by_error_count": file_counter.most_common(5),
    }


# 进阶版本：合并多进程处理 + 过滤低频错误
import concurrent.futures

def analyze_logs_parallel(log_dir: str, max_workers: int = 4):
    """多进程并行分析，适合 TB 级别的日志"""
    all_files = glob.glob(f"{log_dir}/**/*.log", recursive=True)
    
    def process_single_file(file_path: str):
        counter = Counter()
        with open(file_path, "r", encoding="utf-8", errors="ignore") as f:
            for line in f:
                if "ERROR" in line:
                    # 提取错误码或其他特征
                    m = re.search(r"\[ERROR\].*?(\w+Error)", line)
                    if m:
                        counter[m.group(1)] += 1
        return counter
    
    final_counter = Counter()
    with concurrent.futures.ProcessPoolExecutor(max_workers=max_workers) as executor:
        futures = [executor.submit(process_single_file, fp) for fp in all_files]
        for future in concurrent.futures.as_completed(futures):
            final_counter.update(future.result())
    
    return final_counter.most_common(20)
```

**关键考点**：
- **内存优化**：使用生成器逐行读取，不使用 `f.readlines()` 将整个文件加载到内存
- **正则优化**：编译正则一次（`re.compile`），避免每次匹配都重新编译
- **大数据扩展**：提及多进程 `ProcessPoolExecutor` 或使用 `pandas`/`LogPai` 等工具应对大规模日志
- **错误容忍**：`errors="ignore"` 处理编码异常

```python
import jsonschema
from jsonschema import validate
import requests


class ApiResponseValidator:
    """API 响应结构校验器"""
    
    ORDER_SCHEMA = {
        "type": "object",
        "required": ["order_id", "status", "items", "total_amount"],
        "properties": {
            "order_id": {"type": "string", "pattern": "^ORD-[0-9]{8}$"},
            "status": {"type": "string", "enum": ["pending", "paid", "shipped", "cancelled"]},
            "items": {
                "type": "array",
                "minItems": 1,
                "items": {
                    "type": "object",
                    "required": ["product_id", "name", "quantity", "price"],
                    "properties": {
                        "product_id": {"type": "integer"},
                        "name": {"type": "string"},
                        "quantity": {"type": "integer", "minimum": 1},
                        "price": {"type": "number", "minimum": 0}
                    }
                }
            },
            "total_amount": {"type": "number", "minimum": 0},
            "address": {"type": ["object", "null"]},
            "created_at": {"type": "string", "format": "date-time"}
        },
        "additionalProperties": True  # 允许扩展字段，向后兼容
    }
    
    def validate_response(self, response: requests.Response, schema: dict = None):
        """校验 API 响应的结构合法性"""
        try:
            response_data = response.json()
        except ValueError as e:
            raise AssertionError(f"Response body is not valid JSON: {e}")
        
        try:
            validate(instance=response_data, schema=schema or self.ORDER_SCHEMA)
        except jsonschema.exceptions.ValidationError as e:
            raise AssertionError(
                f"Response schema validation failed:\n"
                f"  Field: {list(e.path)}\n"
                f"  Error: {e.message}"
            ) from e
        
        return response_data
    
    def validate_list_response(self, response, item_schema, min_count=0, max_count=None):
        """校验列表响应"""
        data = self.validate_response(response, {
            "type": "object",
            "required": ["data", "total"],
            "properties": {
                "data": {
                    "type": "array",
                    "minItems": min_count,
                    "maxItems": max_count,
                    "items": item_schema
                },
                "total": {"type": "integer", "minimum": 0},
                "page": {"type": "integer"},
                "page_size": {"type": "integer"}
            }
        })
        assert data["total"] == len(data["data"]), \
            f"total={data['total']} 与实际返回数量 {len(data['data'])} 不一致"
        return data
```

**方式二：手写简易校验（考察编程能力）**

```python
def validate_simple_schema(data: dict, schema: dict, path: str = "$") -> list:
    """简易 JSON 结构校验，返回所有错误列表"""
    errors = []
    
    for key, rule in schema.get("properties", {}).items():
        current_path = f"{path}.{key}"
        
        if key not in data:
            if key in schema.get("required", []):
                errors.append(f"{current_path}: 缺少必填字段")
            continue
        
        value = data[key]
        expected_type = rule.get("type")
        
        if expected_type == "object":
            errors.extend(validate_simple_schema(value, rule, current_path))
        elif expected_type == "array":
            if not isinstance(value, list):
                errors.append(f"{current_path}: 期望数组，实际为 {type(value)}")
            else:
                item_schema = rule.get("items", {})
                for idx, item in enumerate(value):
                    errors.extend(validate_simple_schema(item, item_schema, f"{current_path}[{idx}]"))
        else:
            if not isinstance(value, expected_type):
                errors.append(f"{current_path}: 期望类型 {expected_type}，实际类型 {type(value)}")
    
    return errors
```

**关键考点**：
- 理解 JSON Schema 的核心概念：类型、必填、枚举、嵌套结构
- 对"extra fields"的处理策略（是否允许额外字段）
- 通过 schema 校验先于业务断言，让测试失败信息更精准

**难度**：⭐⭐⭐ 困难
